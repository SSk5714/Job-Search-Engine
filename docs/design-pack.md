# JobPilot Europe — Design Pack

Markdown copy of the design pack. The editable version with the architecture, state-machine
and wireframe diagrams lives in Claude Docs:
https://claude.ai/code/artifact/6d621ef4-65c5-4beb-8a93-897cd651f005

Sections marked **(as built)** reflect Phase 1 decisions that differ from the first draft.

## 1. Overview

One FastAPI backend with a deterministic orchestrator, task-specific workers and a separate
monitor, all sharing one PostgreSQL database. Claude is called only for language tasks, and
every AI output is schema-validated before it touches the database. No submission happens
without an approval bound to exact document and form-value hashes.

Principles:

- **State lives in PostgreSQL.** Workers return validated results; only `domain/transitions.py` writes application state.
- **Deterministic by default.** Scheduling, dedup, eligibility rules, scoring arithmetic, transitions and monitoring are plain code.
- **Fail visible, never silent.** Every task attempt, error and alert is a row. Unknown outcomes stop the workflow.
- **Mock first.** Every external integration has a mock adapter so the pipeline runs and tests offline.

## 2. Architecture

Processes from one codebase: API (FastAPI), Celery worker pool, Celery beat with the
orchestrator schedule (Phase 5), and the monitor (Phase 5). Redis carries tasks; PostgreSQL
holds all state. External services: job sources, Claude API, application portals.

```
Web UI (Next.js) ──HTTPS──> API (FastAPI, auth, transitions) ──> PostgreSQL
                                   │ enqueue run                     ▲
                                   ▼                                 │ writes (orchestrator only)
                             Redis queue ──> workers: discovery │ matching │ documents │ preparation
                                                     │             │           │            │
                                                Job sources     Claude API  Claude API  Apply portals
Monitor (own scheduler, heartbeat) ──reads──> PostgreSQL, Redis
```

See the repository tree in `README.md`. Backend, workers and monitor share one Python

## 4. Database schema (as built)

24 tables (Phase 2 added `app_settings`). UUID keys, `created_at`/`updated_at`, append-only history.

| Group | Tables |
| --- | --- |
| Identity | users |
| Profile | candidate_profiles, profile_versions, profile_facts |
| Jobs | job_sources, search_configs, search_runs, jobs, job_match_evaluations |
| Applications | applications, application_state_history, documents, form_fields, approvals, submission_attempts, follow_ups, recruiter_interactions |
| Operations | agent_runs, task_attempts, error_events, health_checks, notifications, idempotency_keys |

Integrity rules enforced in the database:

| Rule | Mechanism |
| --- | --- |
| A job URL is stored once | unique `jobs.url_normalized` |
| A source's job id is stored once | unique `(source_id, external_id)` |
| One active application per job | partial unique index on `applications.job_id` where state not terminal |
| One running run per search | partial unique index on `search_runs.config_id` where running and no overlap allowed |
| One valid approval per application | partial unique index on `approvals` where not invalidated |
| One successful submission per application | partial unique index on `submission_attempts` where succeeded |
| A transition applies once | unique `application_state_history.idempotency_key` |
| One evaluation per job, profile version and model | unique `(job_id, profile_version_id, model_version)` |

**(as built)** An application row is created when a job is discovered (state `discovered`),
so every job has one pipeline item and its full history from the start. Cross-source
duplicates (same company, title, city) are stored with `duplicate_of_id` and get no
application; closed listings are stored and get no application.

**(as built)** Migrations: one autogenerated baseline (`0001_baseline_schema`) with a
tested downgrade, instead of four split revisions. Seed data is applied by
`python -m jobpilot.bootstrap` (also run at API startup), not by a migration, so it can be
re-run safely.

Retention: browser evidence 90 days after close; documents until the application is deleted;
descriptions of never-applied jobs 180 days; error events and task attempts 90 days.
Retention jobs arrive in Phase 6.

## 5. API contracts

REST under `/api/v1`, JSON, OpenAPI at `/docs`. Writes need `X-Requested-With: jobpilot`
(CSRF). State-changing calls need an `Idempotency-Key`; a replay returns the stored response
with `Idempotent-Replay: true`, a reused key with a different body returns 422.

| Method + path | Purpose | Phase |
| --- | --- | --- |
| POST /auth/login, /auth/logout, GET /auth/me | Session cookie | 1 ✅ |
| GET /profile, PUT /profile | Current version; save a new version | 1 ✅ |
| POST /profile/facts/{id}/verify, GET /profile/versions | Verification, history | 1 ✅ |
| GET /sources, PATCH /sources/{code} | Source labels; enabling unbuilt adapters is refused | 1 ✅ |
| GET/POST /search-configs, PATCH /search-configs/{id} | Saved searches | 1 ✅ |
| POST /search-runs, GET /search-runs, GET /search-runs/{id} | Start and inspect runs; 409 on overlap | 1 ✅ |
| GET /jobs, GET /jobs/{id} | Filtered list with latest evaluation | 1 ✅ |
| POST /jobs/{id}/decision | approve, reject or later | 1 ✅ |
| GET /applications, GET /applications/{id}, PATCH /applications/{id} | Tracker, detail, follow-up and outcome | 1 ✅ |

| GET /applications/export.csv | CSV export | 1 ✅ |
| PATCH /applications/{id}/form-fields/{field_id} | Edit a value; invalidates approval | 1 ✅ (UI in 4) |

Error shape: `{"error": {"code", "message", "details"}}`. Codes include
`invalid_transition`, `forbidden_actor`, `guard_failed`, `approval_required`,
`approval_stale`, `unresolved_fields`, `run_in_progress`, `stale_version`,
`submission_outcome_unknown`, `idempotency_key_required`, `idempotency_key_reused`,
`csrf_failed`, `unauthenticated`, `validation_error`, `not_implemented`.

## 6. Agent contracts

Pydantic models in `jobpilot/schemas/agents.py` (discovery, built) and section 5 of the
Docs version (matching, documents, preparation, monitor alert). Claude calls in later phases
use tool use with JSON schemas generated from the same models; schema failure is a failed
attempt, never a partial write.

**(as built, Phase 2)** Claude matching (`claude/match-v1/<model>/w<settings-hash>`) uses
structured outputs via `client.messages.parse()`. Claude only extracts track, seniority, skills mapped
to verified fact ids, language and other requirements, each with a verbatim quote. Code discards
fact ids that are not in the verified snapshot and quotes not found in the posting, then computes the
score with the same arithmetic as the rules matcher. Per-run and daily USD budgets apply; on any AI
failure the job is scored by rules and the fallback is written into the explanation and the error log.

**(as built)** Phase 1 matching is `rules-v0` (`domain/scoring.py`): keyword rules over
**verified** facts only, with evidence per point, hard eligibility rules separate from the
score, and the 30/25/20/10/15 weights. Recommendations: 75+ apply, 55–74 review, below 55 low
priority; any uncertain eligibility caps at review, any failed rule rejects, senior roles are
low priority.

## 7. Workflow rules

See `jobpilot/domain/states.py` (table) and `transitions.py` (guards). Highlights:

- Only the user moves `classified → approved_for_preparation`; only the orchestrator marks `submitted`, and only with a fresh approval and a succeeded attempt.
- `needs_manual_input` and `failed` can only return to the state they interrupted.
- Every transition locks the row, checks rule and guard, writes history and bumps `state_version` in one transaction.
- Approval stores SHA-256 hashes of each ready document and of the sorted form values. Any edit invalidates it; submit recomputes and refuses on mismatch.
- An `unknown` submission attempt blocks further attempts until checked by hand.

## 8. Security model

| Threat | Control | Status |
| --- | --- | --- |
| API key exposure | Server env only; frontend proxies `/api/v1` and never sees backend secrets | ✅ |
| Unauthorized access | Argon2 password hash, signed HttpOnly SameSite=Strict cookie | ✅ |
| CSRF | SameSite=Strict plus required custom header on writes | ✅ |
| Duplicate actions | Idempotency keys stored in the same transaction as the change | ✅ |
| Prompt injection | External text stored as data, never instructions; AI returns proposals only | Phase 2–4 |
| Browser steering | Per-application domain allowlist, no file:// or private IPs | Phase 4 |
| Session theft | Fresh isolated Playwright context; user signs in directly | Phase 4 |
| Login brute force | Rate limiting | Phase 6 |
| Runaway cost | Token budgets per run and per day | Phase 2 |
